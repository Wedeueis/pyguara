# Working on a PyGuara game with a coding agent

How to point Claude Code, Codex, Cursor or anything else that speaks MCP
at a PyGuara project, and what it can do once it is there.

Two halves, which are independent — the instruction files are useful on
their own, and the live surface works without them:

1. **Instruction files**, so the agent knows what a PyGuara scene is
   before it does anything.
2. **The operation surface**, so it can read and edit a scene rather than
   guessing at files.

## 1. Instruction files

```bash
pyguara studio instructions
```

That writes, in the project root:

| File | For | Contents |
| --- | --- | --- |
| `AGENTS.md` | the cross-tool standard | everything |
| `CLAUDE.md` | Claude Code | `@AGENTS.md` and anything Claude-specific |
| `GEMINI.md` | Gemini CLI | `@AGENTS.md` and anything Gemini-specific |
| `.cursor/rules/pyguara.mdc` | Cursor | a rule that defers to `AGENTS.md` |

### Why one file and three shims

`AGENTS.md` is the cross-tool standard, and the nearest one in the
directory tree wins for the code being edited. The others exist because
their tools do not read it:

- **Claude Code** reads `CLAUDE.md`, and falls back to `AGENTS.md` only
  when there is no `CLAUDE.md`. It does not merge them — if both exist,
  `CLAUDE.md` wins outright. So the shim is an **import line**, not a
  copy. A copy becomes a second source of truth that rots while looking
  authoritative.
- **Cursor** reads `.cursor/rules/*.mdc`. The older `.cursorrules` is
  legacy.
- **Gemini CLI** reads `GEMINI.md`.

### Hand-written content is safe

Everything outside the generated markers is preserved exactly:

```markdown
# my_game

## Hard-won knowledge

Do NOT touch the collision layers: see issue #412.

<!-- BEGIN GENERATED BY PYGUARA STUDIO -- edit outside this block -->
...regenerated every time...
<!-- END GENERATED BY PYGUARA STUDIO -->
```

A file with no markers is appended to, never replaced. Running the
generator twice touches nothing the second time, so it stays out of your
git diff.

### Keeping them current in CI

```bash
pyguara studio instructions --check
```

Exits non-zero and names what is stale. Only the generated region is
compared, so a hand edit elsewhere is not drift — it is the point.

### Size

Codex truncates an instruction file at 32 KiB, silently. The generator
warns past that and suggests the fix: move detail into a nested
`AGENTS.md` beside the code it describes, since the nearest file in the
tree wins.

It never writes `AGENTS.override.md`. That filename belongs to whoever
needs to override what the generator produces.

## 2. The live operation surface

Instruction files tell an agent how the project works. The operation
surface lets it work *on* a running one — read the entity graph, change
it, run the game, look at the result.

### Over MCP

Register `pyguara studio mcp` as a stdio MCP server. For Claude Code:

```json
{
  "mcpServers": {
    "pyguara-studio": {
      "command": "pyguara",
      "args": ["studio", "mcp", "--project", "."]
    }
  }
}
```

Needs the `studio` extra:

```bash
uv sync --extra studio    # or: pip install -e .[studio]
```

### Without MCP

The same operations, JSON lines on stdin and stdout, no extra dependency:

```bash
$ echo '{"op": "scene_summary"}' | pyguara studio ops
{"ok": true, "operation": "scene_summary", "result": {...}}
```

This is the contract; MCP is a transport over it. See
[ADR 0002](../adr/0002-studio-agent-transports.md) for why that way round.

!!! note "stdout is the protocol"
    Both servers reserve stdout and send everything else to stderr. A
    plain engine boot writes five lines of prose — pygame's import banner
    and the engine's console logger — straight into the stream otherwise,
    and the reader on the other end sees a parse error and blames the
    protocol.

### What an agent should do first

The generated instructions say this, but it bears repeating:

1. `project_overview` — scenes, prefabs, components, assets.
2. `scene_summary` — counts for the open scene. `scene_tree` is the full
   read and is large.
3. `component_schema` before setting a field on a type it has not used.
   It carries the field types, the defaults, and an enum's valid members —
   the one thing it cannot guess.

### Three conventions that make it workable

**Entities are named by id**, and ids survive undo, redo and reload. An id
from one call still means the same entity in the next.

**Every edit returns its diff**, so "did that do what I meant?" is
answered in the reply rather than costing another call.

**Errors name the alternative.** The error text *is* the recovery path:

```
No entity 'playr'. Did you mean 'player'?
No component named 'Transfrom'. Did you mean 'Transform'?
Transform has no field 'rotatoin'. Did you mean 'rotation'?
'FLOATY' is not a BodyType. Valid values: DYNAMIC, KINEMATIC, STATIC.
'set_field' has no argument(s) ['componet']. Valid arguments: [...]
```

That last one matters more than it looks. Every schema refuses unknown
arguments, so a typo'd argument name is an error rather than a silently
ignored key — an operation that reports success without doing what was
asked is the most confusing failure an agent can get, because the reply
says it worked.

## Running an agent you do not fully trust

```bash
pyguara studio mcp --mode ask --journal .studio/journal.jsonl
```

In `ask` mode every edit is queued rather than applied, carrying **the
diff it would produce** — so you decide against the consequence rather
than the request. Approve or reject them from the Journal panel, or from
`approvals` over the wire. A rejection reason goes in the journal, where
the agent can read it back and learn what not to propose again.

In `plan` mode nothing is applied at all and every edit comes back
described. Useful for "tell me what you would do".

Either way the journal records every action and who asked for it,
including the failures, and every applied edit is undoable through
`history`.

## The closed loop

What the whole thing is for: an agent making a change and checking it
without anyone at the window.

```
find_entities   {"id_contains": "player"}
set_field       {"entity_id": "player", "component": "Transform",
                 "field": "position", "value": {"x": 400, "y": 100}}
run_frames      {"frames": 20}
capture_frame   {"name": "after"}
history         {"operation": "undo"}
```

`run_frames` returns a diff of what the simulation moved. `capture_frame`
writes a PNG and says whether the frame — and the world buffer behind it —
is a single flat colour, which is how a broken render path shows up.

Frames are a fixed sixtieth of a second and the RNG is seeded, so the same
script twice produces the same result. That is what makes "run it again
and diff" an answer rather than a coin toss.

!!! warning
    A capture proves the render *path* works. It does **not** prove a
    window appears on screen; those have already diverged in this engine.
    See [Visual Inspection](agent-visual-inspection.md).
